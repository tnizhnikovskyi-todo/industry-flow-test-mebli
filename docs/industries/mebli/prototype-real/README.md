## 2. Як відтворити
Середовище C-00 (`tools/odoo/`) у репо відсутнє; база збиралась прямими командами, рівнозначними `shoot/build_db.sh` (перестворення бази перед зйомкою, установка, оновлення з `--i18n-overwrite --load-language uk_UA`, seed з явним `env.cr.commit()`, перевірка кількості записів):
```
source /home/user/odoo19/env.sh
dropdb --if-exists demo-mebli-sample
$ODOO_PY $ODOO_BIN -c $ODOO_CONF -d demo-mebli-sample -i td_mebli_demo --load-language uk_UA --without-demo=True --stop-after-init
$ODOO_PY $ODOO_BIN -c $ODOO_CONF -d demo-mebli-sample -u td_mebli_mrp,td_mebli_sale,td_mebli_cutting,td_mebli_dashboard,td_mebli_demo --load-language uk_UA --i18n-overwrite --stop-after-init
$ODOO_PY $ODOO_BIN shell -c $ODOO_CONF -d demo-mebli-sample < package/addons/td_mebli_demo/scripts/seed_showcase.py
psql -d demo-mebli-sample -c "SELECT count(*) FROM purchase_order_line"     # > 0 (3), інакше seed не закомічено
$ODOO_PY $ODOO_BIN -c $ODOO_CONF -d demo-mebli-sample --http-port 8072 --workers=0
cd docs/industries/mebli/prototype-real/shoot
BASE=http://127.0.0.1:8072 DB=demo-mebli-sample DEMO_EMAIL_DOMAIN=demo-fabryka.example ORDER_ID=123 LATIN_OK=mebli,sample ONLY=0 node scenario.mjs
BASE=http://127.0.0.1:8072 DB=demo-mebli-sample DEMO_EMAIL_DOMAIN=demo-fabryka.example ORDER_ID=123 LATIN_OK=mebli,sample node rec_clips.mjs D_sample
```
Після останнього перестворення бази (2026-11-12) модуль `td_mebli_sale` двічі оновлено (`-u td_mebli_sale --i18n-overwrite`) лише заради колонок і підпису вкладки «Закупівлі під замовлення» — дані не змінювались; перед повним обсягом база перестворюється заново.
`ORDER_ID` — замовлення з посиланням клієнта «Кухня й шафа-купе, квартира» (seed `td_mebli_demo/dates.py`). `LATIN_OK=mebli,sample` — ім'я бази `demo-mebli-sample` у прихованому меню користувача навбару (на екрані не видно; `rec_lib.latinWords` його бачить).

## 8а. Переробка зразка за 0.2.1 — що змінено і чому
Власник: «зачем закупка в сейл ордере?» Урок 0.2.1 (§23, «Стандарт перш за все» — зворотна перевірка): перевіряти не лише «у стандарті є X», а й «чи не дублює `td_` те, що вже веде стандартний модуль». Попередній зразок завів закупівлю в замовлення на продаж — це паралельний облік (FAIL), не «борг на потім».

| Було (зразок 0.2.0) | Стало (0.2.1) | Чому |
|---|---|---|
| Модель `td.mebli.order.item` у замовленні на продаж: постачальник, дата постачальника, стан, «днів на встановлення» — ввід руками | моделі немає; замовні позиції — товари з маршрутами MTO + «Купити», постачальник і строк у прайсі постачальника; підтвердження замовлення створює закупівлі (стандарт) | дані закупівлі веде модуль Закупівлі; другий облік розходиться з першим |
| Дата постачальника — поле позиції в `sale.order` | дата — `date_planned` рядка закупівлі, ввід лише в модулі Закупівлі (комірник) | один документ — одна правда |
| «Днів на встановлення» (нове поле) | стандартний `produce_delay` специфікації | стандартний аналог є (`PLAN.md` §2) |

## 9. Обмеження
- Прогнозна дата враховує цех (кінець МО) і закупівлі під замовлення; порізку в дистриб'ютора — ні (повний обсяг, S-04).
- Готовність за закупленою позицією рахується від старту МО (`produce_delay` усієї специфікації) — для фасадів, що ставляться наприкінці, песимістично (`PLAN.md` §7).
- Смарт-кнопку «Купівлі» бачать лише користувачі групи «Закупівлі: користувач» (стандарт `sale_purchase`); менеджер салону цієї групи не має і читає закупівлі своїх замовлень на вкладці (правило доступу `td_mebli_sale`).
- Мобільний показ, дашборд, решта 14 екранів — після приймання зразка.
