# Зауваження: A-12 / A-13 спроба 2 — перевірки скілів після A-11 (2026-11-13)

- Кроки: A-12 (`config-as-code@0.3.1`, наряд `tests/naryad/A-12-2.yaml`, `params.mode: fix`), A-13 (`master-data-template-builder@0.3.1`, наряд `tests/naryad/A-13-2.yaml`). Тестова база — локальний Odoo 19.0 CE, як у спробі 1 (`observations/2026-11-13-a12-a13-local-odoo-instead-of-mcp.md`).
- Знахідки (б):
  - `flow-core/skills/flow-autocheck/scripts/autocheck.py` `p_vendored_license` (рядки ~465–467): перелік `package/addons` бере всі записи, зокрема файл `AC-COVERAGE.md` (A-11), і вимагає в ньому LICENSE → **хибний FAIL** `vendored-license` у A-12. Пропозиція: брати лише каталоги з `__manifest__.py`.
  - `master-data-template-builder/scripts/check_master_data.py` `FILE_RE = ^(\d{2}b?)_…`: третій прохід тих самих `id` (`05c_…`) скрипт мовчки не бачить. Обхід — номер за порядком імпорту (`td/19b`, `20b`, `21b` для `td_bas_code`). MD-order для двопрохідних `NNb` — той самий хибний FAIL, що в спробі 1 (тепер і `01b`).
  - `master-data-template-builder` Крок 1: режим «повтор» описано лише для `returned_from: A-14` (правки CHECKS.md). Повтор після ескалації через брак модулів A-11 (`returned_from: A-11`) не описано — виконано як «перший запуск для нових td-довідників, стандартні файли без змін». Крок 8 каже, що `td/` не імпортуються («потрібні модулі A-11»), — коли модулі є в гілці, імпорт `td/` можна робити (зроблено додатково, 0 помилок).
  - `config-as-code` Крок 6 / `config-kinds-odoo19.md`: `td_param` описано лише як `ir.config_parameter` (`td_<пакет>.vp_xx`). Після A-11 VP — поля `res.company.td_*`; використано `kind: td_param` з `model: res.company`, `xmlid_target: base.main_company`, якір `res.company:xml_id=base.main_company:<поле>`. Потрібен рядок формату для «td_param → поле компанії» і правило для кількох компаній.
  - `config-as-code` Крок 7: read-back `settings` через `default_get` не бачить полів `related` на компанію (`portal_confirmation_sign`, `attendance_kiosk_use_pin`) — у першому прогоні агент отримав хибну розбіжність. `apply-semantics.md` згадує якір `related`; варто прямо написати: «читати створений запис `res.config.settings` або поле компанії, не `default_get`».
  - CFG-td-isolation проти A-11: модулі кажуть «дані конфіг-пакета» для `td_milestone` (AC-019) і `td.mebli.accrual.reason` (AC-107) — правило скіла це забороняє (питання — `tests/open-questions.md`).
  - Скілів `odoo19-mvp-build:config-review`, `boost:odoo19-lint`, `boost:source-check` у сесії й далі немає → за таблицею статусів A-12 не може бути `done` у тестовому режимі взагалі.
- Пропозиція (г): власникам пакета — виправити `p_vendored_license` і `FILE_RE`/MD-order; додати в `config-package-format.md` вид «td_param → поле res.company»; описати режим A-13 для `returned_from: A-11`.
